# VIIMsignal AX 대화 문맥 엔진 기획

문서 버전: 1.0  
작성일: 2026-09-04  
대상 릴리스: VIIMsignal 1.0

## 1. 목적

사용자가 한 번의 질문으로 끝내지 않고, 앞선 분석을 기준으로 기간·제품·채널·지역·지표를 좁히거나 비교하며 의사결정을 이어갈 수 있게 한다.

현재는 `conversationId`를 기준으로 질문과 답변을 저장하고 다시 보여주지만, 다음 질문을 해석할 때 이전 메시지와 분석 조건을 LLM에 전달하지 않는다. 따라서 대화 화면은 이어져도 `그중`, `같은 제품`, `서울만`, `지난달과 비교` 같은 후속 표현을 안정적으로 이해하지 못한다.

1.0 목표는 다음과 같다.

- 같은 대화에서 앞선 분석 조건을 안전하게 상속한다.
- 사용자가 새로 말한 조건은 이전 조건보다 우선한다.
- 원천 데이터 전체가 아니라 구조화된 문맥만 모델에 전달한다.
- 회사·워크스페이스·사용자 권한을 넘는 문맥은 절대 재사용하지 않는다.
- 단순 후속 질문은 LLM 없이 처리하고, 모호한 질문에만 LLM을 사용한다.
- 모든 해석 조건과 실행 행동을 감사 가능한 형태로 저장한다.

## 2. 사용자 경험

### 기본 흐름

1. 사용자가 `최근 30일 가장 많이 팔린 제품을 보여줘`라고 질문한다.
2. AX는 `판매수량 × 제품 × 최근 30일`을 조회하고 결과를 표시한다.
3. 사용자가 `그중 서울 매장만`이라고 질문한다.
4. AX는 이전의 지표·제품·기간을 유지하고 지역만 서울로 변경한다.
5. 사용자가 `지난해 같은 기간과 비교해줘`라고 질문한다.
6. AX는 현재 조건을 유지하면서 비교 기준을 전년 동기로 추가한다.

### 화면 표시

AX 패널 상단에 작은 문맥 요약을 표시한다.

`최근 30일 · 판매수량 · 제품별 · 서울 · 전체 채널`

후속 질문으로 조건이 바뀌면 변경된 항목만 짧게 알린다.

- `지역을 전체 → 서울로 변경했습니다.`
- `기간과 제품 조건은 이전 분석에서 이어받았습니다.`

사용자는 다음 행동을 할 수 있어야 한다.

- `조건 초기화`: 현재 대화는 유지하고 분석 조건만 초기화
- `새 대화`: 메시지와 분석 문맥을 모두 새로 시작
- 문맥 항목의 `×`: 제품·지역·채널 등 특정 조건만 제거
- `근거 보기`: 상속한 조건, 새로 입력한 조건, 조회 기준일 확인

## 3. 문맥의 범위

문맥은 반드시 다음 네 가지 키에 종속된다.

- `organization_id`
- `workspace_id`
- `user_id`
- `conversation_id`

워크스페이스를 전환하면 기존 대화 문맥은 자동으로 사용하지 않는다. 다른 페이지로 이동하는 것은 허용하되, 현재 사용자가 해당 페이지를 볼 권한이 있을 때만 문맥을 이어간다.

## 4. 저장할 문맥

새 테이블 `ax_conversation_contexts`를 두고 대화당 최신 문맥 1행을 유지한다.

```json
{
  "version": 1,
  "pageKey": "hub",
  "intent": "compare_sales",
  "metric": "quantity",
  "dimension": "product",
  "visualization": "bar",
  "period": {
    "kind": "rolling",
    "days": 30,
    "start": null,
    "end": null,
    "comparison": "previous_year"
  },
  "filters": {
    "country": "KR",
    "channel": null,
    "location": "서울",
    "platform": null
  },
  "subjects": [
    {"type": "product", "key": "ARC-07", "label": "Utility Jacket"}
  ],
  "lastQuerySpec": {},
  "lastResultSummary": {
    "rowCount": 12,
    "topKeys": ["ARC-07", "FLOW-22"],
    "watermark": "2026-09-04T08:40:00Z"
  },
  "pendingAction": null,
  "summary": "최근 30일 제품별 판매수량을 서울 지역으로 좁혀 전년 동기와 비교 중"
}
```

저장하지 않는 정보:

- 주문 원문 전체
- 고객 이름, 전화번호, 상세 주소, 이메일
- 대량의 조회 결과 행
- 사용자가 볼 권한이 없는 제품·매장·채널
- API 키 또는 연결 비밀정보

기존 `ax_messages.query_spec`과 `visualization_spec`은 당시 답변을 재현하고 감사하기 위한 스냅샷으로 계속 유지한다.

## 5. 서버 처리 흐름

### 질문 수신

`POST /api/ax/query`

기존 요청 형식은 유지한다.

```json
{
  "conversationId": "uuid",
  "question": "그중 서울 매장만 보여줘",
  "page": "hub",
  "filters": {}
}
```

### 처리 단계

1. 로그인, 회사, 워크스페이스, 페이지 권한을 검증한다.
2. `conversationId`가 현재 사용자와 워크스페이스 소유인지 검증한다.
3. 최근 메시지 8개와 최신 구조화 문맥을 불러온다.
4. 현재 페이지 필터와 문맥을 합친다.
5. 명확한 후속 질문은 규칙 엔진으로 처리한다.
6. 대명사·비교 기준·의도가 모호할 때만 OpenAI 라우터를 호출한다.
7. 허용된 지표와 필터만 남기도록 서버에서 다시 검증한다.
8. Supabase에서 실제 권한 범위 데이터를 조회한다.
9. 답변, 조회 명세, 시각화 명세, 갱신된 문맥을 저장한다.
10. 응답에 상속·변경된 조건을 함께 반환한다.

### 응답 확장

```json
{
  "conversationId": "uuid",
  "answer": "서울 매장으로 범위를 좁혔습니다.",
  "resolvedContext": {},
  "contextChanges": [
    {"field": "location", "from": null, "to": "서울", "source": "user"}
  ],
  "inherited": ["metric", "dimension", "period", "subjects"],
  "plan": {},
  "data": {},
  "timing": {}
}
```

## 6. 문맥 병합 규칙

우선순위는 다음과 같이 고정한다.

1. 현재 질문에서 사용자가 명시한 조건
2. 현재 화면에서 직접 선택한 필터
3. 같은 대화의 구조화 문맥
4. 페이지 기본값

예외 규칙:

- `처음부터`, `조건 초기화`, `전체로`는 해당 문맥을 제거한다.
- 제품이 바뀌면 이전 제품별 결과의 `그중` 참조를 제거한다.
- 페이지 권한이 없으면 이전 문맥에 대상이 있어도 조회하지 않는다.
- 데이터 기준일이 변경되면 캐시를 무효화한다.
- `이대로 승인`, `200개로 바꿔 승인`은 마지막 `pendingAction`에만 연결한다.

## 7. LLM 사용 원칙

### LLM을 사용하지 않는 경우

- `서울만`, `제품별로`, `7일로 바꿔줘`
- 저장된 수요예측·할인추천·리뷰 신호 조회
- 동일한 질문의 캐시가 유효한 경우
- 명확한 필터 추가·제거

### LLM을 사용하는 경우

- `왜 매출이 달라졌어?`
- `그중 위험한 것부터 판단해줘`
- `재고와 마진을 같이 보면 어떤 선택이 좋아?`
- 여러 지표를 조합해야 하는 비교·원인·전략 질문

모델에는 다음만 전달한다.

- 현재 질문
- 최근 대화 최대 8개 메시지의 짧은 텍스트
- 최대 1,200자의 대화 요약
- 최대 2KB의 구조화 문맥
- 허용 지표·차원·시각화 스키마

LLM이 SQL이나 데이터 값을 직접 만들지 못하게 하고, 구조화된 조회 계획만 반환하게 한다. 숫자와 실행 가능 여부는 항상 서버와 DB가 결정한다.

## 8. 속도와 비용 기준

- 규칙 기반 후속 질문: 목표 1초 이내
- 캐시된 질문: 목표 500ms 이내
- OpenAI가 필요한 질문: 목표 8초 이내
- OpenAI 타임아웃: 4.5초 후 규칙 기반 폴백
- 최근 메시지: 최대 8개
- 장기 요약: 최대 1,200자
- 입력 토큰 예산: 대화당 요청 최대 약 4,000토큰
- 동일 문맥·질문 캐시: 15분

캐시 키에는 `workspaceId`, 질문, 문맥 버전, 필터, 데이터 기준일을 포함한다.

## 9. DB 변경안

```sql
create table public.ax_conversation_contexts (
  id uuid primary key default gen_random_uuid(),
  organization_id uuid not null references public.organizations(id) on delete cascade,
  workspace_id uuid not null references public.workspaces(id) on delete cascade,
  conversation_id uuid not null references public.ax_conversations(id) on delete cascade,
  user_id uuid not null references auth.users(id) on delete cascade,
  context_state jsonb not null default '{}'::jsonb,
  context_summary text,
  context_version integer not null default 1,
  source_message_id uuid references public.ax_messages(id) on delete set null,
  updated_at timestamptz not null default now(),
  unique (conversation_id)
);
```

필수 인덱스:

- `(organization_id, workspace_id, user_id, updated_at desc)`
- `(conversation_id)` 고유 인덱스

RLS는 현재 사용자가 소유한 `ax_conversations`이고 해당 워크스페이스의 활성 멤버인 경우에만 조회·수정할 수 있도록 설정한다.

## 10. 프론트엔드 변경안

- `state.axContext`: 현재 구조화 문맥
- `state.axContextChanges`: 이번 질문에서 바뀐 조건
- 패널 헤더 아래 문맥 칩 표시
- 답변 위에 `이전 분석에서 이어받음` 표시
- `새 대화`와 `조건 초기화`를 구분
- 페이지 이동 시 같은 대화는 유지하되 권한과 워크스페이스를 다시 검증
- 응답을 기다리는 동안 기존 메시지 높이를 유지해 대화창 흔들림 방지

## 11. 테스트 시나리오

### 기능

1. 첫 질문 뒤 `그중 서울만`이 이전 기간·지표를 상속한다.
2. `최근 7일로 바꿔줘`가 기간만 변경한다.
3. `제품별 대신 채널별`이 차원만 변경한다.
4. `전체 채널로 초기화`가 채널 필터만 제거한다.
5. 페이지 이동 후에도 허용된 문맥이 유지된다.
6. 새 대화에서는 이전 제품과 필터가 상속되지 않는다.
7. `이대로 승인`이 마지막 실행 후보에 연결된다.
8. 오래된 대화가 요약된 뒤에도 핵심 조건이 유지된다.

### 보안

9. 다른 사용자의 `conversationId` 요청은 404 또는 403으로 차단된다.
10. 다른 워크스페이스의 대화 문맥이 조회되지 않는다.
11. 제한된 채널·국가·위치가 이전 문맥을 통해 복원되지 않는다.
12. 고객 직접 식별정보가 모델 입력과 로그에 포함되지 않는다.

### 장애·성능

13. OpenAI 타임아웃 시 현재 문맥으로 규칙 기반 결과를 반환한다.
14. 문맥 저장 실패가 사용자 답변 자체를 잃게 하지 않는다.
15. 동일 후속 질문은 캐시에서 500ms 이내 반환된다.
16. 50개 메시지 대화에서도 전달 토큰 예산을 넘지 않는다.

## 12. 개발 순서

### P0 — 1.0 필수

1. `ax_conversation_contexts` 마이그레이션과 RLS
2. 문맥 조회·병합·검증 라이브러리
3. `/api/ax/query`에 최근 메시지와 문맥 연결
4. OpenAI 구조화 출력 스키마에 문맥 변경값 추가
5. 답변과 문맥의 원자적 저장
6. 패널 문맥 칩, 조건 초기화, 새 대화 UI
7. 워크스페이스·권한·후속 질문 자동 테스트

### P1 — 안정화

8. 장기 대화 요약과 토큰 제한
9. 문맥 기반 캐시 키와 데이터 기준일 무효화
10. 응답 시간·모델 호출·폴백률 운영 모니터링
11. 실제 데이터 리허설 질문 세트 실행

### P2 — 이후 고도화

12. 여러 지표의 근거를 묶는 자연어 분석 합성
13. 팀 공유 대화와 의사결정 회의 링크
14. 사용자가 허용한 개인 선호 기억

## 13. 완료 기준

- 후속 질문 20개 테스트에서 문맥 상속 정확도 95% 이상
- 회사·워크스페이스·사용자 간 문맥 누출 0건
- 규칙 기반 후속 질문 p95 1초 이내
- OpenAI 포함 질문 p95 8초 이내 또는 정상 폴백
- 모든 답변에서 적용된 기간·필터·데이터 기준일 확인 가능
- 질문에서 승인·실행까지 동일 대화 ID로 감사 추적 가능
- 운영 리허설에서 대표·MD·재고 담당자의 실제 연속 질문 시나리오 통과

## 14. 제품 결정

VIIMsignal 1.0에서는 `대화를 길게 생성하는 챗봇`보다 `이전 분석 조건을 정확히 이어받는 의사결정 인터페이스`를 우선한다. LLM은 문맥과 의도를 해석하고, 데이터 집계·권한·실행 가능 여부는 기존 서버와 Supabase가 담당한다.
